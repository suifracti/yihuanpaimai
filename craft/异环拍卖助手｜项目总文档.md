## 文档维护协议｜强制

- **Read before write**：每次项目结论/下一刀/Craft 同步前，先读本页 + 对应当前主题页；只有追溯原因时才读历史归档，不凭聊天记忆直接追加。
- **更新优先于追加**：新结论替代旧结论时原位更新；旧结论移入历史归档。已完成的旧‘下一刀’、等待中的旧审计、失效 TODO 不得继续留在当前页。
- **根页零流水账**：根页只放当前页面入口和历史归档入口；日期日志、Codex 回报、测试过程、长段总结全部进入开发日志归档。
- **单一 current authority**：同一事实只保留一个当前权威位置，其它页只做引用/摘要。历史页里的‘当前/下一步’永远只代表当时。
- **每轮只记状态变化**：只同步新 commit/verdict、边界或产品决策变化、blocker 变化、当前下一刀变化、正式冻结/淘汰方案；普通讨论和临时猜测不写当前页。
- **当前下一刀只能有一个**：其它未来工作只进入路线队列；流程固定为审计 → 最小修复 → 关键回归 → 独立 commit → 停止 → 更新当前状态。
- **页面膨胀即压缩**：一旦出现明显重复/历史过程过多，就保留结论、边界、当前状态，把过程移归档，不等到几百条再整理。
- **写后自检**：检查根页是否新增流水账、当前页是否有新旧冲突/重复、当前下一刀是否仍唯一并与最新代码/审计一致。冲突权威顺序：最新代码+实测 > 本页 > 对应当前主题页 > 历史归档 > 聊天旧记忆。
- **换行格式门**：Craft 多行内容必须使用真实 block / 真实换行，禁止把转义字符写进正文；每次写入后搜索项目中的“反斜杠+n”字面量，异环项目命中必须为 0 才算同步完成。
- **写入预算**：默认每轮 Craft 只允许修改 1 个当前主题页，新增/改写最多 3 个要点；超过预算必须先合并、替换或删除旧内容，禁止靠继续 append 解决。
- **禁止日期流水章节**：当前页不新增 YYYY-MM-DD｜本轮完成 式章节；commit/verdict 直接更新原有状态。完整过程只有在用户明确要求保留时才进入专项历史页。
- **长度硬门**：当前状态页或主题页一旦明显需要长滚动才能找到结论，下一次写入前必须先 compaction；除非用户明确要求全面整理/完整审计，否则不得以大段总结形式同步。

- settlement verified=171；truth confidence high=39，说明“字段存在”不能自动等价于高置信 truth。`Settlement Truth Evidence v1` 已冻结：同一 OCR 流的 5 帧稳定 + 截图/hash 只能证明观测稳定与证据完整性，不能单独升级为独立 `high` truth；正式 high-confidence truth 需独立人工确认或真正独立 verifier。进一步冻结：Tier 3 review 通过 Truth Gate **不等于** 整条 record 已 formal-eligible；实施前必须用未来真实 parent record 形态跑完整 Evaluation Eligibility validator，确认 parent schema/lifecycle/admission/temporal/target 等其它 gate，不得直接承诺 `formallyEligibleCount > 0`。

## History Admission / Evaluation Gate

`Prediction Evaluation Artifact v1` 仍冻结；Legacy/Shadow 结果继续仅作 exploratory evidence。A1 variance 路线与 Upper-tail / State Support Audit 均未得到可生产因果结论。Upper-tail capture contract、runtime hook 与 readiness preflight 已在 commit `3bfc8614be9c0b89ed1bd9ace05ccd47068ab02a` 收口为 `READY_FOR_NATURAL_COLLECTION`，`realValidPairCount=0`；未来正常使用时被动积累 NATURAL_RUNTIME_CAPTURE + independent reviewed truth，在此之前算法支线 parked，不修改 state support、likelihood、value model、variance 或 Gold cap，也不发布新的 accuracy。

History admission 与 evaluation eligibility 必须分离：`record exists ≠ history admitted ≠ evaluation eligible ≠ high-confidence ground truth`。Shared `History Admission Policy v1`、Prediction Snapshot v1 / Settlement Truth Evidence v1 validators 已冻结；probable duplicate、legacy timestamp、truth evidence 与 prediction temporal/target/mode provenance 继续统一 fail-closed 或返回 reason code。

- Main/评估管线都必须有 versioned admission policy；排除 DRAFT/cancelled/diagnostic，处理 duplicate 与 legacy timestamp。
- finance 不能直接信任 raw `realizedProfit/acquired/purchaseSpend`；需要统一 acquisition/payment/cost semantics 后再做净收益/消耗。
- History 页面只是 UI；真正前置条件是 persisted record contract 与 admission。

## Prediction Evaluation｜BLOCKED_BY_DATA_PROVENANCE

Main Analysis 当前所有真实性能指标继续 `NOT_AVAILABLE_YET`。当前合法的只有 admitted match count/date series 与通过字段级 Truth Gate 的历史事实；MAE、Median AE、relative error、Bias、quantile calibration/coverage、underestimation rate、Red-tail、direction accuracy、extreme hit、Grade，以及净收益/消耗均不得发布。正式评估仍必须由离线 versioned pipeline 生成 frozen summary artifact，Main 只读 summary，不现场 replay Solver。

- Benchmark v1/v2 不得当生产 prediction accuracy。
- 旧历史数据并非‘不能用’：仍可用于 Historical empirical prior、候选空间/分布建模、趋势与探索性分析、legacy benchmark/回放诊断，以及后续模型改进；当前禁止的仅是把 provenance 不完整的 legacy rows 直接计入正式 publishable Prediction Evaluation 指标或与新 formal-eligible 样本混算。正式成绩单与历史研发用途必须分轨标记。
- 零散 saved predictions 不足以直接算正式 MAE：solver version、prediction provenance、settlement confidence 不统一。
- Overview performance strip 与 Analysis 必须消费同一个 evaluation summary，不能各算一套。

## 未来正式评估指标

- 基础：MAE / Median AE / relative error / Bias / calibration / coverage，并按信息模式与高价值场景分层。
- 用户特别关心低估：`underestimation_error=max(0,(actual-estimate)/actual)`；统计 >10% rate、>20% catastrophic rate，并单独看高价值/大红尾部。
- “少估不超过 10%”目前是质量方向，不是逐局硬保证；允许失败比例要由真实 admitted + high-confidence truth 数据后冻结。

## 估值器 ≠ 出价策略

异环估值器目标是尽量准确、校准良好，不因怕亏故意低估；保守/平衡/进取只属于 Decision Layer。AP/达芙蒂尔的保守用户体感不能成为异环 estimator 的目标函数。

## 当前算法已知风险 / 待验证

- unlocked Red 对额外未知 R 的 soft geometric attenuation（历史实现如 `0.24^(i-1)`）在 R>=3 可能过度衰减；目前缺足量完整 itemized truth，不拍脑袋改，继续冻结。
- 未来需把 Red conditional value distribution 与 state likelihood 分开验证，避免把“少见”错误编码成“价值更低”。
- HeavyTail/IQR、AP structural prior、bitset 等只作为 baseline/性能实验；进入 production 前必须 time-safe walk-forward 或同输入回归证明收益。

## 数据飞轮

`真人局 → Canonical MatchRecord → 高质量 settlement truth → Historical Dataset → Prediction Evaluation → 模型/Decision 改进`。优先降低真实数据采集与验证摩擦，不用单样本手调 heuristic。

## P20 / P50 / P80 语义警告

- 当前 Solver/Shadow 中的 P20/P50/P80 首先是**价值分布的分位数/区间语义**，不是天然的三种‘准确率百分比’。

- Direction accuracy、Extreme hit rate、Grade/B+ 的业务定义与评分 rubric 也尚未冻结。

`DaphneAssistantEstimator` 根据 `TotalPurpleGoldRedCount + PurpleCount + AverageGoldValue` 枚举 GoldCount，由总数推 RedCount，再用 bitset subset-sum reachability 判断该 G 是否存在合法金价组合。

# Warehouse Vision v1 架构设计与实现计划

## 当时目标

在冻结 Shared Core / Market / Shadow / FSM / Live DB 的前提下，独立构建 Warehouse Vision v1，专注右侧仓库视觉网格的精准、可信感知。核心目标是建立证据分层模型，禁止 `candidates[0]` 强制选优；无法唯一确定时输出候选集合与价格区间。

## 当时安全边界

- 不修改 Shared Core、Market 预测模型、Shadow 逆向求解器、FSM、Live DB。
- 不复制 AuctionPilot 源码、图片或 catalog，只独立借鉴设计思想。
- 当时计划新建 `core/warehouse_vision.py`。

## Evidence 分层

`UNKNOWN → OUTLINE_ONLY / RARITY_ONLY → RARITY_AND_SHAPE → CANDIDATE_SET → UNIQUE_IN_CATALOG / EXACT_IDENTIFIED`

- UNKNOWN：未揭示、暗色或无法确认。
- OUTLINE_ONLY：只知道连通块尺寸。
- RARITY_ONLY：只知道品质。
- RARITY_AND_SHAPE：品质与尺寸完整。
- CANDIDATE_SET：品质 + 尺寸得到候选集合。
- UNIQUE_IN_CATALOG：该组合在图鉴中唯一。
- EXACT_IDENTIFIED：多候选时，经模板匹配高置信锁定具体身份。

## 3~5 帧稳定确认

当时计划维护 `SlotHistoryBuffer`：连续 N∈[3,5] 帧品质/尺寸一致，且连通域 IoU ≥ 0.80 才提升为 confirmed，以过滤发光、粒子、扫光与单帧闪烁。

## 多候选模板匹配

当时计划使用 `cv2.matchTemplate(..., cv2.TM_CCOEFF_NORMED)`。若 Top1 ≥ 0.85 且 Top1-Top2 ≥ 0.08，则 `EXACT_IDENTIFIED`；否则保留完整候选、价格池与 `[min,max]`。

## 红/金高价值通路

当时计划对高价值金/红藏品做独立通路，多尺度 0.9x~1.1x + 边缘/梯度加权，提高重尾藏品召回。

# 大厅 OCR / 四方视觉架构审计

## 我们当时的链路

HUD 点击刷新 → WebView/WS → 主进程 broadcast → 视觉 worker watcher 只设置 `pending=True` → 当前 `process_frame()` 继续执行 → 下一轮循环头 `reset_session_state()` → 截图 → scene fast classify → 大厅三路 RapidOCR → 写 current_context → HUD。

## 当时实测

- `_classify_scene_fast`：约 33.6ms。
- `lobby_venue_chip`：稳态约 1.55s。
- `lobby_tool_chip`：稳态约 1.64s。
- `lobby_character_chip`：约 1.5–2.2s。
- 三路串行一次：约 4.3–6.2s。
- `auction_main_canvas` 1843×1058 近整屏 OCR：约 8.8s。

## 第一次刷新仍是旧角色的根因

刷新不是即时识别事务，只是 pending flag。当前阻塞 OCR 不会被中断；HUD 点击时也不会主动清旧值。OCR 空结果时旧 `lobbyCharacter` 还可能继续保留，因此用户看到第一下还是旧角色、第二下才更新。

## 当时发现的错误稳定策略

- alias / fuzzy match 越加越多。
- 小X 一律猜小吱。
- 曾存在“小吱 → 达芙蒂尔”特殊防跳逻辑，会直接阻挡真实切换。

## ok-nte

角色使用头像模板/特征匹配；当前角色还有颜色/形状 fast path；截图与识别线程解耦；OCR 只用于必须读的小字。关键思想：角色身份是有限集合，不把名字 OCR 放在热路径。

## NTE Drive Calc

用户触发扫描；角色模板 + 驱动盘形状模板；OCR 读属性/词条；有 vision_worker / streaming_pipeline 等独立扫描流水线。静止界面不持续 OCR。

## MaaNTE

MaaFramework 任务图；拍卖 BidKing 基本由按钮级 TemplateMatch / ColorMatch 构成，局部 OCR 还带 expected 白名单。`wait_freezes` 用于稳定画面，热路径可做到 0 OCR。

## 当时形成的新架构方向

`截图 → 场景快检 → ROI 变化门 → 闭集模板/分类 → 低置信才 OCR fallback → generation/stale result 管理 → HUD`

核心目标：静止画面尽可能 0 OCR；角色切换 100–300ms 级；一次刷新对应一次新事务；失败显示未识别而不是回落旧角色；稳定依赖帧/Evidence，不依赖角色名字特判。

## 2026-08-18｜产品方向 QA：fallback 用“具体可能状态”而不是粗区间

用户明确认为 fallback 的“粗略可能价值区间”没有实际意义。Shadow 无法充分发力时，更希望看到若干个**具体可能状态 / 场景**，例如：

- 可能性 1
- 可能性 2
- 可能性 3

每个可能状态都应同时给出该状态下的价值拆分，而不是只给一个总区间：

- 推算金价 / 金色价值
- 推算红价 / 红色价值
- 推算紫价 / 紫色价值
- 白 / 绿 / 蓝混合价值推断
- 总价值 / 对应推荐出价（若需要）

这类输出的重点是**把“为什么可能值这个数”拆开给用户看**，让用户能判断某个候选状态是否合理，而不是只给一个宽泛区间。

因此后续 fallback 方向应优先考虑：从 Exact State / 当前已知事实 / 历史先验中选出若干最有代表性的可行状态，逐个展示品质价值组成与依据；不要把一个宽区间当作信息不足时的主要答案。

Full Shadow 仍以 P20 / P50 / P80 概率分布为主；Shadow coverage 不足时则切到“若干具体可能状态 + 分品质价值拆解 + 有依据的推荐出价”这一类结构化 fallback。

## 2026-08-18｜产品方向 QA：价值分布优先，部分情报也要给可依赖结果

用户明确认为 `SafeBuy / RecommendedMax / ChaseLimit` 这类三档报价不够客观，不应作为产品核心输出。`RecommendedMax` 可能还有一点实用价值，但也不应压过价值分布本身。

### 核心输出

产品首先回答：**这箱货可能值多少。**

优先展示：

- P20
- P50
- P80
- 必要的候选价值范围 / 概率区间
- 当前推断依据与不确定性

不再把“安全价 / 建议最高价 / 极限追价”作为默认核心 UI。

### Shadow 无法充分发力时

仍然需要一个**补位的推荐出价**，不能因为 Shadow coverage 不足就完全不给行动参考。但 fallback 也不能脱离结构事实胡乱给值，尤其不能出现明显离谱、用户无法依赖的推荐。

因此后续需要设计：Full Shadow 时以 P20/P50/P80 等客观价值分布为主；Partial / Structural 时仍输出一个有边界、有依据、明确低置信度的 fallback 推荐，而不是直接空白或假装成完整 Shadow。

### OCR 与悬浮窗都需要改

当前 OCR 模式存在一个明显产品问题：例如只有 `goldAvg` 时现在可能直接不给算。用户不希望这种交互继续存在。

OCR 与 Manual Overlay 都应该遵循同一原则：**有多少可信事实，就尽量算到对应层级；信息不完整时降级，但不要轻易完全失去输出。**

最终目标不是“缺一个字段就停止”，而是让 Full Shadow / Partial / Structural / fallback 之间形成连续、可依赖的降级链。

## 2026-08-18｜产品方向 QA：网页与悬浮窗职责分离

用户希望网页与悬浮窗不必做成同一套 UI 的缩放版，而是按使用场景分工。

### 悬浮窗

定位为**极简局内工具**。优先只保留真正会影响计算、需要快速手填/修正的数字与结果，例如：

### 最新真人手测暴露的新问题：Shadow Coverage Gate

有数据的局目前实测基本没有明显问题；真正麻烦的是历史概率分布不足的局。

最新样本中：页面存在 10 个候选结构，但只有 1 个具备整仓概率分布，另外 9 个只有结构约束。唯一有分布的 State 为 `G=13 / P=7 / R=0`，其 `P20=P50=P80≈51.55W`，页面却仍把 51.55W 包装为正式“预计整仓价值 P50”。该局真人实际价值约 100W。

这暴露出一个更上游的统计语义风险：若缺失分布的 State 被直接排除，剩余少数有历史数据的普通 State 可能被误当作整个候选空间的 Whole P50。缺失并非随机，稀有 / 高价值结构恰恰更可能缺历史样本，因此存在 Missing-State / Missing-Not-At-Random Bias。

当前已让 Gemini 只做 Coverage Gate 审计，不先改算法：确认 unsupported State 是否被排除、聚合分母如何定义、原始 state weight 是否保留；新增 `supportedStateCount / totalStateCount / supportedWeight / totalWeight / coverageRatio` 的设计；统计 coverageRatio 与误差、高价值 False Fold 的关系，再提出 Full Shadow 合法门槛。Coverage 不足时应降级 Structural，并把现有 51.55W 改为“已覆盖状态条件 P50”，不能继续冒充整仓完整 P50。

#### 🎮 真人对局流程与验收标准

## 真人实际对局流程（用户亲自说明）

### 1. 拍卖大厅

这是正常待机页。

可见 / 可配置内容包括：

- 当前拍卖场地
- 当前竞拍助手 / 角色
- 当前仪器组合，例如「高级品鉴仪器组」
- 「开始匹配」按钮

点击「开始匹配」后开始下一局。

### 2. 匹配确认弹窗

点击开始匹配后，会出现确认提示，例如“匹配成功后将扣除入场费，是否继续”。

特点：

- 有「取消 / 确认」
- 用户通常约 0.5 秒就点确认
- 该状态不能成为完整生命周期的硬依赖
- OCR / scene 如果漏掉，可以记录“未捕获”，但不能阻塞后续进入对局

### 3. 进入对局 Loading

确认后进入 Loading。

Loading 右侧类似「拉冬」「粉爪银行」之类文字属于随机 Lore / 世界观信息，会变化，不是 venue，也没有业务价值。

这一阶段只需要知道：`scene = AUCTION_LOADING`。

### 4. 抽箱 + 场地条件

Loading 后会先进入抽取本局规则的阶段。

这里会一起确定：

- 本局箱型 `box`
- 本局场地条件 `fieldCondition`

例如可能抽到琉璃宝箱、实木宝箱等，同时确定标准对局 / 加倍 / 一手情报等条件。

箱型和场地条件属于本局重要固定信息。

### 5. 正式局内画面布局

正式竞拍画面主要分三块。

**左侧：4 名玩家**

- 玩家角色头像
- 玩家名字
- 每名玩家下方有 1 / 2 / 3 / 4 / 5 等历史回合槽位
- 槽位下面显示该玩家对应历史回合的出价，可能是 `500K` 这种缩写，也可能是具体数字

**中间：公开情报 / 仪器情报**

- 拍卖师公开情报
- 千眼其一
- 其它局内仪器 / 情报卡

注意：这些局内情报不等于大厅仪器组合，也不等于 v0.6 `toolGroup(group1/group2)`。

**右侧：Warehouse**

- 显示本局仓库的当前可见视口
- 仓库内容是随机的，也可能因使用道具而新增 / 暴露信息
- 右侧仓库需要滚轮向下滚动才能看到完整内容
- 单帧只代表当前可见仓库，不能假设未滚动区域

**底部：箱型 + 场地条件**

- 一般显示本局 box 和 fieldCondition
- 某些时刻可能只显示箱型、条件不显示
- 如果画面没有条件，不应强行默认 standard；应保持 unknown，除非其它明确画面已经确认过本局条件

### 6. 回合推进与历史出价

正常拍卖按回合推进。

用户确认的规则：

- 通常有第 1～5 回合
- 前 4 回合存在提前拿下整局的倍率机制
- 第 5 回合通常由最高价拿下全部拍品
- 如果第 5 回合出现同价，则可能进入第 6 回合，只由同价玩家继续竞价
- 第 6 回合若再次同价则流拍

左侧每名玩家的历史槽位天然提供：`player × round → bid`

因此理论上可以重建整局每个玩家每个回合的历史报价。

### 7. 当前回合出价结束后的四人最终报价

每回合大家完成出价后，左侧会出现四名玩家这一回合的明显大数字报价。

例如：

- 500,000
- 400,000
- 591,498
- 886

这里可用于：

- 当前回合四人最终报价
- 当前最高报价
- leader
- 与历史槽位互相校验

OCR 必须特别注意：

- `K` 单位
- 六位数
- 极小的一位 / 三位数报价
- 当前大数字与历史小槽位是两种不同视觉布局

### 8. Warehouse 在局内的变化

Warehouse 内容随机，且可能因为局内道具而逐渐显示更多信息。

当前阶段只要求准确记录“当时真实可见的 Warehouse 状态”，不提前假设完整仓库。

滚动前后必须区分视口位置，旧 slot 不能错误累积成越来越多不存在的藏品。

### 9. 竞拍结算界面

结算画面是本局最终真值的重要来源。

**左侧信息**

- 获胜玩家的**局外角色头像**
- 头像右边是**玩家名字**
- 价格区域包含：最终成交价、实际价值、收益
- 另有奖励金
- 玩家对应的**拍卖助手**是另一个独立字段

必须严格区分：

- 玩家角色头像
- 玩家名字
- 拍卖助手

它们不是同一个概念。

**右侧 Warehouse**

- 仍然是本局 Warehouse
- 同样需要滚轮才能看到完整仓库

**结算 OCR 要求**

- 等最终动画数字稳定后再 finalize
- 不能把动画早期的中间 actualValue 当最终真值
- profit 必须保留正负号
- 一局只 finalize 一次

### 10. 点击退出

在结算页点击退出后，会进入一次 Loading，然后回到拍卖大厅。

### 11. 回大厅后的仪器补全

退出回大厅后，通常还会做一次补充操作。

**补全流程**

1. 大厅
2. 点击「高级品鉴仪器组」区域
3. 打开「仪器组合」页面
4. 点击「一键补全」
5. 确认是否消耗金贝珠一键补全
6. 自动回到大厅
7. 再点击「开始匹配」进入下一局

这个“一键补全确认”和匹配确认类似，也可能只停留很短时间，不能作为核心 OCR 生命周期的硬依赖。

### 当前完整循环

`AUCTION_LOBBY → 匹配确认（可选瞬时态） → AUCTION_LOADING → 抽箱 / 场地条件 → IN_AUCTION R1 → R2 → R3 → R4 → R5 / 提前结束 / 必要时 R6 → SETTLEMENT → 退出 Loading → AUCTION_LOBBY → 仪器组合 / 一键补全（可选大厅子流程） → AUCTION_LOBBY → 下一局`

### 当前定义的 OCR / Vision 完成标准

在不依赖估值算法的前提下，一局结束后至少应能可信还原：

- 大厅场地 / 竞拍助手 / 仪器组合
- 本局 box + fieldCondition
- round / timer
- 4 名玩家
- 每名玩家各回合历史报价
- 每回合最终报价
- leader / 当前最高报价
- 中间公开情报
- 当前可见 Warehouse 及滚动变化
- 结算获胜玩家、玩家名、拍卖助手、成交价、实际价值、正负收益、奖励金
- 从大厅进入、完成竞拍、结算、退出、回到大厅的完整生命周期

在以上信息真人局可稳定记录之前，不继续推进估值算法。

## 可信证据模型

每个槽位/连通块不应直接从“看见颜色+尺寸”跳到具体藏品，而应明确区分证据强度：`UNKNOWN → OUTLINE_ONLY / RARITY_ONLY → RARITY_AND_SHAPE → CANDIDATE_SET → UNIQUE_IN_CATALOG / EXACT_IDENTIFIED`。

## 候选与模板

- `(品质 + 尺寸/形状)` 只负责过滤候选，不等于身份。
- 严禁 `candidates[0]` 盲选。
- `CandidateCount == 1` 才能直接标记图鉴唯一。
- 候选 >1 时才做像素级模板比对；若 Top1 不够高或没有显著领先，保留候选集合和价格区间。

## 时序稳定

品质、尺寸、轮廓等信息应通过 3–5 帧稳定确认，避免动画/发光/扫光造成单帧误判。

## AuctionPilot（小吱助手）右侧仓库定向研究结论

核心差距不是“模板少”，而是我们缺少完整的**仓库空间模型**。

- 我们当前更接近：`画面 → blob → trackId → 品质 / 尺寸 / 候选`
- 小吱助手更接近：`画面 → Board → 规则 Grid → Viewport Slot → Scroll Offset → Physical SlotId → Warehouse Ledger → Evidence / Identity`

### 小吱助手更稳的关键层

- **Board / Grid 测量**：默认不是只靠固定 ROI；存在 `MeasureGrid / ColumnCenters / RowCenters / CellRect` 等结构，先在 Board 内量规则网格
- **物理仓位账本**：区分 `ViewportRow/Column` 与真实 `Row/Column/SlotId`，将当前视口映射到整仓物理槽位
- **滚动对齐**：通过滚动条位置、fine offset、相邻帧对齐把视口滚动换算成物理行偏移
- **覆盖确认**：维护顶部 / 中部 / 底部和确认百分比；没有完整覆盖时不把当前视口当成整仓
- **Evidence 分层**：品质、轮廓、候选集、唯一图鉴、Exact Identity 分层推进；证据不足就保持 unknown / candidate set
- **遮挡冻结**：出价键盘 / 动画出现时冻结仓库布局、品质和扫描进度，关闭后短暂保护旧状态再恢复扫描

### 我们可以保留的部分

- Evidence 分层方向
- 品质色分割
- 轮廓 / 形状稳定后再确认
- 未锁定形状时不强行锁图鉴身份
- 已修正的 Warehouse ROI

### 当前层级不对的部分

- `trackId` 跟的是屏幕 blob，不是物理 SlotId；滚动后同一件容易被当成新件
- `crop_width / 10` 粗估格子，容易出现 6×2、6×5 之类离谱尺寸
- `GridCalibrator` 的固定 1080p 25 格预览不是完整 10×25 物理仓库
- 每帧只输出当前可见 blob，没有整仓 Ledger

## Warehouse 新实现顺序

1. **Board + Grid**：在现有 `warehouse_board` 内测出真实规则网格，得到列中心、行中心、单格尺寸。
2. **Viewport Slot**：把当前可见藏品变成 `(col,row,w,h,rarity,evidence)`，先保证静止画面尺寸和格位稳定。
3. **Scrollbar → Physical Offset → Ledger**：视口行 + offset → SlotId，按物理槽位合并，解决滚动重复计数。
4. **Coverage + Overlay Freeze**：确认整仓覆盖；出价弹窗 / 动画时冻结旧状态。
5. **Candidate / Identity**：只在品质 + 轮廓已确认后再做 Shape / 图鉴 / Exact Identity。
