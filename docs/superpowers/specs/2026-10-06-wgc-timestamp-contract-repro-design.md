# WGC来源时间契约与同帧最小对照

本轮只研究契约、现有投影和自建窗口。生产候选仍为`50d6ae8+clock-startup/3bb434ba037e`，不改其门禁或覆盖编译产物。
原反例`build/native_qa/live-af63072614/`保持：2次尝试、1帧接受，第二次在读回前拒绝2239000ns未来来源值。

## 要区分的假设

1. 当前C#/WinRT投影改变ABI的Duration。用同一活帧的直接IDirect3D11CaptureFrame getter与投影值对照。
2. 比较的是不同帧或属性值发生变化。只从池取出一次，持有帧直到全部读取与读回完成；QI得到相同IUnknown身份，读取前后重复核对。
3. 来源异常只限于游戏渲染环境，或普通自建窗口也发生。同一窗口仅绘制固定背景和会话随机编码，不使用桌面内容；正常条件未复现只能限定本次条件。
4. 来源时间与画面因果新鲜度不是同一个命题。请求QPC后由本程序绘制唯一编码，记录Paint前后QPC，从该帧像素解码编码。仅对测试窗口可独立证明请求后绘制；不得外推为游戏证明。

## 数值与同帧证明

记录调用方请求QPC、出池前后、每次getter前后、投影ticks、直接ABI Duration、重复getter、帧IUnknown与所查询接口的IUnknown相等性、ContentSize、读回时间、像素hash、编码及Paint时间。
接口IID与vtable签名须核对微软公开生成代码；直接getter绕过TimeSpan.FromAbi但不绕过Windows的同一个原生属性实现。
不是两套独立的来源时钟；两路相等只能排除本次投影改变数值，不能证明原生生产者正确。

## 一次实验的边界

独立进程创建且只采自身WinForms HWND，CreateForWindow不枚举/选择其他窗口，不激活、无全局输入、无Engine/FRAME/SOURCE/正式历史。
父进程在GO前绑定kill-on-close Job，工作上限8秒、实际退出核实上限10秒。最多3次显式取帧请求，失败计数；没有第二轮自动试验。
绘制640×360纯色与编码；FramePool最多2帧，依次持有1帧。未来来源仅作为诊断反例，不发布为业务接受帧，不等待时间追上再接纳。
首次身份/映射/权限/ABI一致性失败结束；未来来源一旦复现，在留齐同帧数值后结束。无新编码可暂时记录旧测试样本，不能当作请求后画面。
实验自身的诊断读回不使用正式选择器接纳，也不构成生产门禁变更。

## 契约核对结果（2026-10-06）

- [微软属性文档源码](https://github.com/MicrosoftDocs/winrt-api/blob/docs/windows.graphics.capture/direct3d11captureframe_systemrelativetime.md)定义为合成器渲染该帧时的QPC时间。Remarks为空；未找到getter返回值必须不晚于读取方当前QPC的明文保证，也未找到允许预测未来时间、误差范围或可以忽略未来值的说明。这是查阅范围内没有找到保证，不是证明所有Windows实现都没有此约束。
- [微软TimeSpan契约](https://learn.microsoft.com/en-us/uwp/api/windows.foundation.timespan?view=winrt-26100)规定Duration为64位有符号整数，单位100ns。不能把Duration再当原始QPC计数除一次频率。来源不是UTC，也不在当前读取处重新建立起点；其QPC基准来自上述属性定义。
- [微软生成ABI代码固定版本](https://github.com/microsoft/windows-rs/blob/317646c941aa18916ffa5daeb4ffd5ffa4cd26f3/crates/libs/windows/src/Windows/Graphics/Capture/mod.rs)确认接口IID `FA50C623-38DA-4B32-ACF3-FA9734AD800E`，SystemRelativeTime为IInspectable后第二个方法，即vtable槽7，返回TimeSpan。此代码描述ABI，不揭示Windows内部时间戳生产实现。
- 当前候选实际Microsoft.Windows.SDK.NET版本10.0.19041.38，SHA256 `0ec371d93798852e36461c8adddbeadce0f963a04752f0b64e54fe19c1c834a7`；WinRT.Runtime版本2.2.0.0，SHA256 `bcf3a14e8712a90837fc5c0d8c8a24696af2bd7f74e9767597ec81ededfb23db`。本机反编译路径为runtime class → ABI getter槽7 → 单个long Duration → TimeSpan.FromTicks(Duration)。`WgcCapture.cs`随后checked(Ticks*100)，没有偏移、浮点换算或重新计时。
- [Win32CaptureSample问题61](https://github.com/robmikh/Win32CaptureSample/issues/61)讨论掉帧、聚集到达和疑似旧内容；[维护者说明](https://github.com/robmikh/Win32CaptureSample/issues/61#issuecomment-1641533481)确认慢消费不会阻塞DWM，可能漏帧。它没有给出未来时间合法性保证或对应修复；报告者有关时间戳造假的段落已自行标为incorrect，不能当证据。本轮GitHub查询记录保留在build，未找到适用于本反例的权威结论；未找到不等于不存在。

属性按过去发生的渲染事件定义，正常情况下预期不晚于读取时刻；但这一推理不是getter上界的明确契约。现有未来门禁属于保守的来源信任检查。保持它可以拒绝异常来源，但不能据拒绝本身断言Windows违约或定位到驱动。

投影反编译、官方文档快照、ABI固定版本和查询记录在`build/native-timestamp-contract-20261006/`。原游戏反例的活帧已经释放，本轮不可能事后对那个COM对象补读原生getter；不能把本轮正常帧的两路一致当作那个游戏帧的两路一致。

## 后续决策：两种问题分别处理

**A：来源时间在未来。** 原比较QPC时刻读取到sourceNs>comparisonNs。这是来源时间可信度问题，与像素变化无关。补读ABI必须针对仍存活的同一帧；补读期间QPC前进不能撤销已经发生的拒绝。

**B：来源晚于请求而内容仍是初始编码。** 本实验请求后设置Counter=1、Invalidate、Update；[Update官方说明](https://learn.microsoft.com/en-us/dotnet/api/system.windows.forms.control.update?view=windowsdesktop-10.0)是同步执行待处理绘制，不是DWM合成或显示呈现完成的确认。OnPaint内记录了绘制起止，却没有每次绘制编号、GDI提交/flush、DWM合成完成、显示Present完成及捕获对象与呈现事件的对应关系。PaintBegin/End还会被后续OnPaint覆盖，不能冒充counter 0和counter 1各自独立的完整呈现时间线。

已有记录能证明：CPU请求先于最后记录的绘制；捕获先读到counter 0、后读到本次nonce的counter 1；counter 1只在请求后启用，故第二张像素对应请求后生成的测试内容。不能证明第一张来自请求前的合成帧，亦不能证明Counter=1已完成显示呈现后还发生了旧帧回退。第一张既可能含池中/合成链路中尚未更新的内容，也可能是请求后对未更新窗口内容的正常合成；当前没有证据区分。第三次未出帧也不能据此定位提交或捕获缺陷。

按原始QPC换算，相对固定请求：最后记录的PaintBegin为+0.6149ms、PaintEnd为+0.6638ms，第1张source为+0.7270ms（counter 0），第2张source为+18.3735ms（counter 1）。CPU绘制结束与第1张source仅相差0.0632ms，且没有提交/呈现完成事件，不能拿这个排序证明DWM应已包含counter 1。这些相对值来自既有raw，没有重做窗口实验。

不要求游戏每张帧像素改变；静止内容可在新的合成帧中重复。正常的来源时间、身份、映射、时序与年龄证据仍按原规则判断。像素相同不单独拒绝为旧帧，像素不同也不单独证明来源可信。此问题B不是游戏未来值拒绝的修复前置条件。
